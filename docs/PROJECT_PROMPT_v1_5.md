## 0. プロジェクト概要

**Local Notebook AI** は、自治体向けに構築する NotebookLM 風・複数ユーザー対応の
ローカルRAG Webアプリケーションである。

- 対象仕様書: `local_notebook_ai_sdd_spec_v1_2.md`（SDD v1.2、マスター仕様）
- 実装プロンプト集: `local_notebook_ai_implementation_prompts_v1_4.md`（Phase 1〜15の
  実装・実運用経験を反映。変更点は同ファイル冒頭の「変更履歴」を参照）
- UIモックアップ: プロジェクトリソースのPNG（User Workspace / Admin Console）
- 実装者: Kohei（単独）。自治体側には技術要員がおらず、
  実装・受け入れテスト・監視・運用判断のすべてをKoheiが担う。

### 技術スタック（v1.4で確定・追加した項目を含む）
- Node.js 24 LTS（現行検証環境はv22。engines警告は出るが機能に影響なし）
- pnpm workspaces monorepo
- Frontend: Next.js + React + TypeScript（`apps/web`, port 3000）
- Backend: NestJS + TypeScript（`apps/api`, port 4000）
- DB: SQLite（WALモード）+ **Drizzle ORM** + **better-sqlite3（v12系固定）**
  - **Prismaは使用しない。** 理由はv1.3時点から変更なし（Prisma CLIのバイナリ
    外部CDNダウンロード問題）。
- **PDF抽出: `pdfjs-dist`（Mozilla公式、保守されている）を使用する。**
  **`pdf-parse`は使用しない。** `pdf-parse@2.x`はAPI全面刷新で旧オプションが
  使えず、`pdf-parse@1.1.4`（旧API互換）は内部の古いpdf.js（2015年頃）が
  実務上多くのPDFで`"bad XRef entry"`エラーになることを実機検証で確認済み。
- DOCX抽出: `mammoth`
- LLM実行環境: Ollama（`http://localhost:11434`）
- パッケージ: `packages/shared`, `packages/storage`, `packages/rag-core`
- 認証: Cookie-basedセッション（サーバー側セッションストア、opaqueトークン）
- CSRF: double-submit cookie方式
- **全APIレスポンスにグローバルなキャッシュ禁止ヘッダー
  （`Cache-Control: no-store, no-cache, must-revalidate, proxy-revalidate`・
  `Pragma: no-cache`・`Expires: 0`）を設定済み。** ブラウザキャッシュにより
  古いログイン状態が表示される不具合を防ぐため（`apps/api/src/main.ts`）。
- **Helmet**（基本セキュリティヘッダー）・**`@nestjs/throttler`**（レート制限:
  グローバル10リクエスト/秒・200リクエスト/分、`/api/auth/login`・
  `/api/auth/change-password`は専用に5リクエスト/分）を導入済み（Phase 16）。
- **E2Eテスト: Playwright**（`e2e/`、`pnpm test:e2e`）。開発環境とは完全に
  分離した専用ポート（Web:3099/API:4099）・専用DB・専用ストレージ・偽Ollama
  サーバーで動作する設計（Phase 17。**実ブラウザでの実行確認は未実施**、
  上記「現在のステータス」参照）。

## 1. 最重要ルール（すべてのやり取りで厳守）

1. Node.js 24 LTSを前提にする
2. pnpm workspacesのmonorepo構成を維持する
3. Frontend = Next.js + React + TypeScript、Backend = NestJS + TypeScript
4. **DBはSQLite + Drizzle ORM + better-sqlite3（v12系固定）を使う。Prismaは使わない**
5. `.env` / `.env.example` で設定管理する（Zodによる型検証・起動時バリデーション必須）
6. ファイル実体はローカル指定ディレクトリに保存する（StorageAdapterで抽象化、将来S3へ移行可能に）
7. 複数ユーザー利用を前提とし、**一般ユーザーは自分のノートブック・ファイル・チャット履歴・RAG実行ログのみ**操作できる
8. 管理者はユーザー・ファイル・モデル・RAG設定・監査ログを管理できる
9. Standard RAGとHyDE RAGの両方を実装する
10. **HyDEで生成した仮想文書は検索用であり、最終回答の根拠にしてはならない**
    （`RagStrategy`インターフェース＋共有`AnswerGenerator`により、HyDE戦略が
    仮想文書を回答生成コンポーネントに一切渡さない設計で構造的に保証している。
    今後この仕組みを変更する際も、この構造的保証を破らないこと）
11. UIは日本語(ja)/英語(en)のi18n形式にする。`/[locale]/...` ルーティング構造は
    Phase 3で先行導入済み
12. XSS、CSRF、RBAC、所有者チェック、ファイルアップロード制限を実装する
13. OllamaへはFrontendから直接アクセスせず、必ずNestJS API経由にする
14. **Dockerを必須にしない**。`npm run dev` / `pnpm dev` と `npm start` / `pnpm start` で動作すること
15. 実装成果物はPhaseごとに、**Zip/tar.gzでまとめず、ファイル1つ1つを個別に出力**する
16. 変更ファイルは差分ではなく、**変更後の完全なファイル内容**として出力する
17. 複数ファイルを1つのMarkdownにまとめない
18. **外部アプリケーション、OSSアプリケーション、GitHubリポジトリ、商用製品、SaaS、ブログ、記事、サンプル実装等のソースコードを、コピー・改変コピー・貼り付け・実質的に再利用してはならない**（ライセンス表記・出典明示があっても同様に禁止）
19. 実装は仕様書に基づいて独自に作成する。公式ドキュメント参照、npmパッケージの通常利用、公式CLIによる雛形生成は許可される
20. 外部コード利用が必要だと判断した場合でも取り込まず、作業を停止して独自実装の代替案を提示する
21. **あるPhaseの完了条件を検証するためにテスト用データ（ユーザー・notebook・file等）が
    必要で、かつそれを作る正規のAPIがまだ存在しない場合、SQLiteへの直接書き込みで
    済ませてはならない。検証に最低限必要な作成・取得APIを、本来のPhaseのスコープを
    超えない範囲で先出しで実装すること**
22. `tsconfig.json` には `esModuleInterop: true` を設定する
23. **（v1.4追加）PDFのテキスト抽出には`pdfjs-dist`を使用する。`pdf-parse`は使わない**
24. **（v1.4追加）NestJSの認可ガード（Roles/Ownership等）は、クラスレベル・メソッドレベル
    どちらにデコレータを付けても機能するように、`this.reflector.getAllAndOverride(KEY,
    [context.getHandler(), context.getClass()])`を使用する。** `this.reflector.get()`
    のみの実装では、クラスレベルのデコレータを見逃す重大なセキュリティ上の欠陥になる
    （実際にPhase 7〜9の間、この欠陥によりマルチユーザー分離が破られていた実例がある）。
    実装後は、クラスレベル・メソッドレベル両方のパターンで実際に拒否テストを行うこと
25. **（v1.4追加）`main.ts`で、全APIレスポンスに`Cache-Control: no-store, no-cache,
    must-revalidate, proxy-revalidate`・`Pragma: no-cache`・`Expires: 0`をグローバル
    ミドルウェアとして設定する。** 認証・セッション関連APIに限らず、このアプリの全レスポンスは
    動的かつユーザー個別の内容であり、キャッシュされるべきものは存在しない
26. **（v1.4追加）マウント時に呼ばれる非冪等/準冪等なAPIラッパー関数**（現在ログイン中の
    ユーザーを取得する関数、CSRFトークン取得関数等）**には、React 18 StrictModeの
    二重実行に対応するため、同時に複数回呼ばれても同一の進行中リクエストを共有する実装
    （in-flight Promiseの共有）を最初から適用する**
27. **（v1.4追加）ログイン状態など、画面のヘッダー等で継続的に表示する情報を確認する
    コンポーネントは、マウント時だけでなく、クライアントサイドの画面遷移
    （pathname変化）のたびにも再確認する。** Next.jsのレイアウトは画面遷移をまたいで
    再マウントされないため、マウント時1回のチェックだけでは、ログイン成功後もヘッダーが
    古い状態のまま残る不具合になる
28. **（v1.4追加）「データが存在しない/権限がない」ことを示す結果と、「取得自体に
    失敗した（今は分からない）」ことを示す結果を、状態として明確に区別する。** 特に
    認証状態の確認は、一時的なサーバー接続不可を「未ログイン」と誤って確定表示しない
    よう、状態を最低3値（例: `"loading" | "known" | "unreachable"`）で管理する
29. **（v1.4追加）`router.push()`によるクライアントサイド遷移は、稀に（原因不明・
    低頻度で）実行されないことがある（0.5節・4.1節参照、未解決事象）。** 特にログイン
    直後など、後続の処理の正しさが重要な画面遷移では、一定時間後に遷移先へ到達して
    いるかを確認し、到達していなければ`window.location.href`による確実なハード
    リダイレクトを行うフォールバックを検討する
30. **（v1.4追加）「プレースホルダーとして後回しにした機能」は、どのPhaseで解消するか
    を明示的に決めてから進める。** 曖昧に「後のPhase」と書くだけでは、どのPhaseにも
    属さないまま見落とされるリスクがある（実際にPhase 3の`/change-password`
    プレースホルダーが、Phase 15完了までどのPhaseにも組み込まれず見落とされた）

実装中に仕様が曖昧な場合は、**セキュリティ > マルチユーザー分離 > 外部ソースコード利用禁止 > テスト用データ作成ルール > 個別ファイル出力方針**の優先順位で判断する。

## 2. 作業時の振る舞い

- 一度に全機能を作らせない。Phase単位で小さく進める
- 各Phase完了時は以下を必ず報告する:
  1. 実行した内容
  2. 生成・変更したファイル一覧（プロジェクト内パス明記）
  3. 各ファイルの個別ダウンロード
  4. 実行したコマンド
  5. 確認結果
  6. 未実装事項
  7. 次のPhase
- 実装済みコードを不用意に壊さない
- 仕様から外れる提案はしない（提案したい場合は、その旨を明示してから代替案として出す）
- **テスト用データはDBへの直接書き込みではなく、正規のAPI経由で作成する**
  （検証用のAPIがまだ無い場合は、そのAPIを最小実装してから使う）
- ダウンロードファイルの配置先が紛らわしい場合（同名ファイルが複数生成される場合等）は、
  依頼者が配置先を取り違えないよう、ファイルごとの配置先対応表を明示する
  （**v1.4補足**: 実際にPhase 9・13・14で`page.tsx`・`admin.json`・`common.json`等の
  重複が発生した。ダウンロード順と対応表の順序を必ず一致させること）
- **（v1.4追加）ユーザー自身の環境（本番相当）に対して、ログイン中のセッションを
  失効させる可能性のあるDB操作（`sessions`テーブルの削除等）を安易に依頼しない。**
  依頼する場合は、それによって現在ログイン中のセッションが失効する可能性があることを
  明示する（実際に、この案内が不十分だったことでユーザーが「原因不明のログアウト」に
  遭遇する事態が発生した）
- **（v1.4追加）不具合の報告を受けた際は、外部要因（ライブラリ、ブラウザ拡張機能、
  タイミング等）を先に疑うのではなく、まず自分が生成したコードを一行ずつ確認する。**
  この会話の中で、キャッシュ・認可ガード・認証状態管理の3つの重大な不具合はいずれも
  「最初から自分のコードを疑うべきだった」という反省を経て発見された

## 4. 既知の未解決事象（v1.4で新設）

2026年9月10日時点で、原因が完全には特定できていない不具合。次のセッションで
この事象の再発報告を受けた場合、以下を踏まえて対応すること。

### 4.1 ログイン後、管理者専用ページへの遷移が稀に失敗する

**症状**：管理者ログイン成功後（APIは`200`、正しいレスポンス）、`router.push()`
での画面遷移が、ごく稀に（再現性低い）実行されず`/[locale]/login`に留まる。

**分かっていること**：
- 観測された`client.error`ログの`destination`は`/ja/admin`（管理者専用の保護ルート）
- `middleware.ts`が、ブラウザとは別にサーバー間で`GET /api/auth/me`を呼び認可判定している
- ブラウザ拡張機能によるページ`unload`イベントへの干渉も観測されており、
  排除できていない

**実装済みの対応（回避策・診断強化）**：
- `POST /api/client-log`で、ブラウザ側だけで検知した問題を監査ログに報告できる
- ログイン画面で、`router.push()`実行から1.2秒後もまだ`/login`に留まっていれば、
  報告した上で`window.location.href`による確実なハードリダイレクトを行う

**次に取り組むべきこと（未着手）**：
- `middleware.ts`側の認可チェック失敗時の詳細ログを`client-log`相当の仕組みで記録する
- ブラウザ拡張機能を無効化した状態での再現性を複数回試行して比較する

この事象に関する報告を受けた場合、**まず自分が生成したコード（フロントエンドの
状態管理、middleware.tsのサーバー間チェック）を疑うことから始め、外部要因
（ブラウザ拡張機能、タイミング）を安易に結論としないこと。**

## 9. よくある落とし穴（詳細は実装プロンプト集v1.4の0.4節を参照）

Phase 1〜15の実装で実際に発生した問題の要点のみ、ここにも転記しておく。

- `tsconfig.json` に `esModuleInterop: true` が無いと、CommonJSパッケージの
  default importが実行時に `undefined` になる（コンパイルエラーにはならないため気づきにくい）
- `better-sqlite3` はv13以降でプリビルドバイナリ配布が廃止されソースビルド必須になる。
  v12系を使うこと
- Drizzleの `DATABASE_URL`（相対パス）は、CLI実行時とアプリ実行時で解決基準が
  食い違う可能性がある。リポジトリルート基準の絶対パスに正規化する処理を挟むこと
- React 18のStrictMode（開発モード）はマウント時の副作用を2回実行する。CSRF
  トークン取得・ログイン状態確認のような非冪等な処理は、同時に複数回呼ばれても
  同一の進行中リクエストを共有する実装にすること
- **（v1.4追加）`pdf-parse`（v1系・v2系問わず）は使用しないこと。実務上多くのPDFで
  `"bad XRef entry"`エラーになる。`pdfjs-dist`を使うこと**
- **（v1.4追加）認可ガードは`this.reflector.get()`ではなく`this.reflector.
  getAllAndOverride(KEY, [context.getHandler(), context.getClass()])`を使うこと。
  `get()`のみでは、クラスレベルに付けたデコレータのメタデータを取得できず、
  所有者チェック・ロールチェックが機能しない重大な欠陥になる**
- **（v1.4追加）認証状態確認API等、動的なAPIレスポンスには、実装の最初の段階から
  `Cache-Control: no-store`をグローバルに設定すること。後から追加すると、ブラウザ
  キャッシュに起因する「ログイン状態が古いまま表示される」不具合の原因調査が
  困難になる**
- **（v1.4追加）ログイン状態を表示するコンポーネントは、マウント時の1回のチェック
  だけでは不十分。同一レイアウト内の画面遷移はコンポーネントを再マウントしないため、
  pathname変化時にも再確認する設計にすること**
- **（v1.4追加）`middleware.ts`が保護ルートの認可判定のためサーバー間で独自に
  認証確認APIを呼ぶ設計の場合、ブラウザ側のセッション確認とは別経路になることを
  意識する（0.5節・4.1節の未解決事象参照）**
